## 3. 关键转折

### 3.1 采集语义不是“画矩形”

最终确认的真机规则：

- 选区范围只由**起点所在行**和**终点高度**决定，横向位置无关；
- 起点/终点 x 完全相同会形成**零宽矩形**，微信不产生选区，因此保留约 12px 水平偏移；
- 终点越过上/下边界并按住时，微信自动滚动，约 13 条/秒，受消息长度影响；
- 多条目/历史不再预先回底，依赖越界自动滚动；
- `--history` 从底部中心向上越界，实测可抓取多屏历史。

### 3.2 真实发送的敌人是焦点

真机失败大多不是发送逻辑，而是：

- 前台窗口被 DSH Desktop 占用；
- 非管理员进程的合成输入被系统丢弃；
- 输入框锚点缺失，点击兜底落空；
- `Ctrl+A` 选区未释放，Enter 覆盖原文。

对应修复：

- `validate-tree --activate` / soak 前激活；
- `SetForegroundWindow` 失败时用 `AttachThreadInput` 强制置前；
- 静态 `input_box_area`；
- 直接粘贴优先，`End` 后再 Enter；
- 发送后回读校验，不确定即停。

### 3.3 去重必须“宁停勿错”

历史窗口比库尾更旧时无法用尾锚点对齐；早期会静默忽略，表现为 `captured>0 / ingested=0 / duplicates=0`。

最终策略：

- `--history` 标记为测试/诊断，允许不入库；
- 生产采集出现上述组合直接判失败并输出 `DEDUP ERROR`；
- 不再为了“看起来成功”而放宽去重。

## 4. 做得好的地方

1. 真机每一步先 dry-run，真实发送只做小批量灰度；
2. 安全边界没有被“自动化便利”侵蚀；
3. 失败优先修复可观测性与回读，而不是盲目重试；
4. 远程控制只留接口和威胁模型，没有为了演示提前开网络端口；
5. 关键决策有测试、ADR 与验收记录沉淀。

## 5. 踩过的坑与代价

| 问题 | 代价 |
|---|---|
| 采集起点反复调整：右侧补集 → 零宽矩形 → 中心起点 | 多轮真机验证 |
| 预回底与自动滚动冲突 | 多条采集退化成一屏 |
| 切会话校验重复采集 | 放大失败面，历史模式下直接报错 |
| GUI 用子进程控制 | 运行中无法安全交互，只能启停/监控 |
| 测试覆盖率贴着 85% 门禁 | 新增代码容易掉线 |
| 前台激活被系统拒绝 | 首轮 live 失败一次，后修复 |

## 6. 当前风险与技术债

1. **采集鲁棒性**：起点/终点依赖固定比例与边界；`drag_start_area` 未校准；自动滚动速度受消息长度影响。
2. **live 循环样本少**：只跑过 1 条，未做多轮 soak；失败/歧义矩阵不完整。
3. **历史入库未实现**：历史采集仅用于测试/诊断。
4. **GUI 能力有限**：无暂停/恢复、无系统托盘；运行中操作 GUI 会抢焦点。
5. **远程控制未实现**：V1.1 需补 token / TLS / Host 校验 / 限速，当前只有策略骨架。
6. **真实发送样本少**：3 次成功不等于长期稳定。

## 7. 如果重来，会改什么

- 先做“采集实验记录器”，把手动拖拽坐标/结果固化为回放用例，再改代码；
- 更早区分“正常采集”和“历史诊断”，避免去重语义互相污染；
- GUI 从第一天就设计成控制协议客户端，而不是子进程壳；
- 覆盖率门禁留出余量，或对 UI 代码单独统计。

## 8. 结论与下一步

V1.0 可以收口：核心链路真实可用，安全边界完整，失败会停下而不是乱发。  
但它仍是**受控灰度版**，不是无人值守成品。

下一阶段优先级：

```text
采集稳定性 > live 多轮 soak > GUI 托盘/暂停恢复 > 远程控制
```
