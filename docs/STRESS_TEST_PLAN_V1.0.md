# 真实环境压力测试方案（V1.0）

日期：2026-11-07
目标：验证微信 PC 4.x 真机环境下，采集、身份、去重、LLM、记忆筛选、GUI 控制与受控发送的稳定性。
范围：只使用测试账号与测试会话；不压真实用户，不做公网远程，不做无人值守群发。

## 1. 非目标

- 不验证图片/语音/文件/引用回复（V1.0 仅文本）；
- 不验证公网远程控制；
- 不做长时间无人值守真实发送；
- 不把测试消息写入正式用户档案。

## 2. 环境基线

| 项 | 要求 |
|---|---|
| OS | Windows 10/11 |
| 微信 | PC 4.x，固定窗口位置/大小/DPI/主题 |
| Python | 3.11+（当前 3.14.7），venv |
| 权限 | 管理员 PowerShell（真实发送/合成输入） |
| 会话 | 测试账号会话，必须在 `real_send_allowlist` |
| 校准 | `first-run` READY；`validate-tree` 必需采集元素通过 |
| API | DeepSeek Key 可用；记录额度/成本 |
| 数据 | 测试前备份 `data/chat_history.db`、`data/memory.db` |

## 3. 测试数据策略

1. 只用测试账号；不引入真实联系人；
2. 消息类型：短句、长句、多行、Unicode emoji、重复串、测试串、快速连发、间隔发送；
3. 每轮记录：时间、消息内容摘要、期望、实际、是否发送；
4. 每次发送前保留 DB 备份；结束后清理测试历史并保留备份。

## 4. 分层执行

### R0 预检（每次环境变更后）

```powershell
python -m wechat_agent first-run
python -m wechat_agent doctor
python -m wechat_agent validate-tree --strict --activate
```

通过标准：无致命 FAIL；采集必需元素（`message_area` / `input_box` / `search_box`）可用。
注意：`chat_title`、`send_button` 是动态锚点，预检不应因空输入框或标题状态误判失败；浸泡预检应只校验采集必需元素。

### R1 真机 dry-run 浸泡

| 项 | 方案 |
|---|---|
| 轮次 | 20 轮起步，稳定后 50 轮 |
| 模式 | 单屏；另做 5 轮 `--multi` |
| 发送 | 绝不发送（`dry_run=true`） |
| 间隔 | 5~20s |
| 检查 | `ok=true`、`failures=0`、`captured/ingested/duplicates` 自洽 |

通过标准：
- 成功率 ≥95%；
- 无错误回复队列增长；
- 无重复发送（dry-run 也不应写 out 假消息）；
- 失败必须显式（禁止静默 0/0）。

已知边界：`--multi` 抓到与库尾不重叠的旧窗口时，会按生产策略报 `DEDUP ERROR`；这是保护，不是丢数据。

### R2 身份与去重矩阵

| 用例 | 操作 | 期望 |
|---|---|---|
| R2-1 对方消息 | 测试账号发新消息 | `in/user`，入队 |
| R2-2 机器人自己消息 | 机器人账号手动发一条 | `self/assistant`，不入队 |
| R2-3 多端自己消息 | 无 sender 前缀消息 | `self/assistant`，不入队 |
| R2-4 重复窗口 | 同一屏连续跑 3 次 | 第二次起 `duplicates>0` |
| R2-5 旧窗口 | 向上滚动后 `--multi` | 显式失败或正确去重，不能误回复 |
| R2-6 昵称变化 | 修改 identity 昵称后验证 | 不误判 self / 对方 |

通过标准：身份误判 0；self 消息不进入回复队列；去重不产生重复 out。

### R3 记忆 worker 压测

| 项 | 方案 |
|---|---|
| 任务 | 100 个合成 task（临时库） |
| worker | `memory-extract --limit 20` |
| 失败注入 | 第一次 LLM 抛错，验证重试 |
| 成本 | 记录调用次数；不灌真实聊天 |

通过标准：
- `processed = queued`；
- 无 pending 泄漏；
- 失败任务按退避重试，最终 failed/done 状态明确；
- 记忆内容不含测试串/寒暄；
- 不发送微信消息。

真实 LLM 只抽样验证 5~10 条，其余用 Fake/静态 selector 压队列。

### R4 GUI / 控制并发

1. 启动 GUI，检查四页签；
2. 启动/停止 dry-run；
3. 开启/关闭 memory worker；
4. 主任务运行时 worker 应让路；
5. 关闭 GUI，确认无 `vrpa_gui_live_*`、无残留 Python 子进程；
6. 测试 `Ctrl+Alt+Q` 紧急停止；
7. 危险区临时解锁后取消，确认主配置未变。

通过标准：按钮均可恢复；临时配置 100% 清理；无残留进程；主配置始终双锁。

### R5 真实发送灰度

| 阶段 | 条数 | 要求 |
|---|---|---|
| R5-1 | 1 | 手动确认收到 |
| R5-2 | 3 | 每次间隔 ≥30s，逐条确认 |
| R5-3 | 10（可选） | 只在 R5-2 全绿后进行 |

每轮：
1. 测试账号先发新消息；
2. 生成一次性临时配置（GUI 或脚本）；
3. `run --live --max-sends 1 --i-understand-risk`；
4. 检查 `sent_count=1`、`failures=0`；
5. 测试账号确认收到；
6. 删除临时配置，确认主配置双锁。

通过标准：
- 发送成功 1/1、3/3；
- 无重复发送；
- 无“可能已发送”歧义；
- 临时配置 100% 清理；
- 失败立即停止。

### R6 长时浸泡（可选）

- 2 小时 dry-run，20s 间隔；
- 监控 DB 大小、任务队列、内存、API 调用；
- 恢复后检查 `first-run` / `validate-tree`；
- 不做长时真实发送。

## 5. 指标与退出条件

| 指标 | 目标 |
|---|---|
| dry-run 成功率 | ≥95% |
| 身份误判 | 0 |
| 重复真实发送 | 0 |
| 临时配置残留 | 0 |
| memory task 泄漏 | 0 |
| 真实发送成功 | 1/1 → 3/3 |
| 失败后残留进程 | 0 |

任一项不达标：停止压测，保留日志/DB 备份，修复后从 R0 重跑。

## 6. 已知阻塞项（正式长测前要处理）

1. `validate-tree --strict` 对动态 `chat_title/send_button` 误判；预检需拆分“采集必需元素”。
2. live 中 LLM 失败会丢失内存队列，消息已入库但未回复；需要持久化队列或失败重放。
3. 测试历史会污染 Prompt；正式压测前清空测试会话或使用独立测试库。
4. GUI worker 与外部 CLI 任务的并发边界需再确认（当前仅避让 GUI 自己的主任务）。
5. 真实发送样本仍少，不能把 3/3 当作长期稳定性结论。

## 7. 建议排期

- D1：R0 + R1（20 轮）；
- D2：R2 身份/去重 + R3 memory worker；
- D3：R4 GUI + R5 1→3 条；
- D4（可选）：R1 50 轮 + R6 2 小时。

## 8. 交付物

- `data/soak_real/*.jsonl` 逐轮结果；
- `data/reports/` 验收记录；
- DB 备份与清理记录；
- 失败样本与 `NEXT` 动作；
- 最终压测报告：通过/失败项、残余风险、是否允许进入下一阶段。
